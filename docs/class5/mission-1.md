# 미션 5-1. 요구 정리와 분배

!!! abstract "이 미션에서 할 일"
    - PO가 Copilot으로 MVP 우선순위와 정책 결정안을 만들고, 결정 못 한 정책은 이슈에서 `@skilleat-labs`(현업 역할 강사)를 멘션해 확인합니다.
    - PM이 이슈 S1~S4를 등록하고 한 사람에 하나씩 배정합니다. BA가 인수 조건을, 개발자가 바꿀 파일과 충돌 위험을 Copilot으로 정리해 이슈에 남깁니다.
    - 모든 Copilot 결과는 사람이 읽고 고친 뒤 이슈에 올립니다.

**소요 시간** 약 12분  **실습 장소** 팀 리포지토리 `room-booking-team<번호>` (VS Code, github.com)  **관련 교안** [역할 카드](index.md#role-cards), [팀 백로그](index.md#backlog)

## 준비

- 모두 VS Code에서 팀 리포지토리 `room-booking-team<번호>`를 열어 둡니다. 브라우저에는 github.com의 팀 리포지토리를 열어 둡니다.
- 3인 팀은 BA가 PM 일도 합니다. 이슈를 만들면서 인수 조건까지 바로 씁니다. S4는 만들지 않습니다.

## 전체 흐름

| 순서 | 누가 | 무엇을 | 언제 시작 |
|---|---|---|---|
| 1 | PO | Copilot으로 우선순위와 정책 결정안 초안, 결정 이슈 등록 | 바로 |
| 1 | PM | 라벨 `스토리`, 이슈 S1~S4 등록, 담당자 배정 | 바로 (PO와 동시에) |
| 1 | 개발자 | 바꿀 파일과 충돌 위험 분석 → 댓글 | 바로 (분석은 S1~S4 목록으로 시작, 댓글은 이슈가 생기면) |
| 2 | PO | 결정 못 한 정책을 이슈에서 `@skilleat-labs`(현업)에게 묻기 | 결정안 초안이 나오면 |
| 3 | BA | 이슈마다 인수 조건 초안 → 검토 → 이슈 본문에 | PM이 이슈를 만들면. 3인 팀은 BA가 이슈를 만들면서 바로 |
| 4 | 모두 | 내 이슈 읽기 | PM이 이슈를 만들면. 완료 기준으로 먼저 시작하고, 인수 조건은 BA가 이어서 보완 |

## STEP 1. (PO) 우선순위와 정책 결정안 초안 만들기

1. VS Code Chat 보기에서 **+**(**New Chat**)를 클릭합니다. Session Target **Copilot**, Agent 선택기 **Ask**를 고릅니다.
2. **+**(**Add Context**) → **Files & Folders**로 `docs/00_현업요청.md`, `docs/01_킥오프_회의록.md`, `docs/02_현행_업무.md`를 추가합니다.
3. Chat에 붙여 넣기

    ```text
    나는 회의실 예약 서비스의 PO입니다. 첨부한 문서만 근거로 아래를 정리해 주세요.

    1. 회의록 "결정한 것" 4개의 MVP 우선순위(1~4위)와 이유 한 줄씩. 근거 문장을 문서에서 인용해 주세요.
    2. "결정하지 못한 것" 3개 각각에 대해
       - 선택지와 각 선택지의 장단점
       - PO 결정안(추천) 한 줄
       - 현업(총무팀)에게 확인할 질문 한 줄
    3. 문서에 근거가 없는 내용은 쓰지 말고 "근거 없음"이라고 표시해 주세요.
    ```

4. 답을 읽고 아래를 확인합니다.
    - 우선순위 1위가 겹침 막기인지 봅니다. 회의록에 "제일 급한 건 겹치는 예약"이라는 말이 있습니다.
    - 결정 못 한 것이 최대 예약 시간, 노쇼 자동 취소, 현황판 연락처 3개인지 봅니다.
    - 문서에 없는 숫자나 정책(예: "최대 3시간")을 지어냈으면 지웁니다.
5. github.com 팀 리포지토리 → **Issues** 탭 → **New issue**를 클릭합니다.
6. 제목을 입력합니다.

    ```text
    [결정] MVP 우선순위와 미결 정책
    ```

7. 본문에 Copilot 답 중 검토한 내용을 붙여 넣고 **Create**(화면에 따라 **Submit new issue**)를 클릭합니다.

확인: 이슈 `[결정] MVP 우선순위와 미결 정책`이 만들어졌고, 우선순위 4개와 질문 3개가 있습니다.

## STEP 2. (PO) 이슈에서 현업(총무팀)에게 묻기

회의록에서 결정하지 못한 정책은 Copilot도, 팀도 정하지 않습니다. 현업에게 묻습니다. 오늘은 강사가 총무팀 담당자 역할을 맡고, GitHub 아이디 **`skilleat-labs`**로 이슈에서 답합니다. 실제 회사에서도 현업 담당자에게 이렇게 이슈로 묻고, 답을 이슈에 남겨 결정 근거로 씁니다.

1. 결정 이슈 `[결정] MVP 우선순위와 미결 정책` 맨 아래 댓글 칸에 붙여 넣고, STEP 1에서 검토한 질문으로 다듬은 뒤 **Comment**를 클릭합니다.

    ```text
    @skilleat-labs 총무팀 담당자님, 회의록에서 정하지 못한 세 가지를 확인 부탁드립니다.
    1. 한 번에 예약할 수 있는 최대 시간: 2시간인가요, 4시간인가요?
    2. 노쇼 자동 취소: 시작 후 10분인가요, 15분인가요? 이번에 넣어야 하나요?
    3. 현황판에 예약자 연락처를 보여도 되나요?
    Copilot 결정안은 위 본문에 있습니다. 이번 MVP(S1~S4)에 넣을지도 알려 주세요.
    ```

2. `@skilleat-labs`를 입력할 때 추천 목록에 안 나와도 그대로 끝까지 입력하면 됩니다. 댓글에서 `@skilleat-labs`가 파란 링크로 보이면 알림이 간 것입니다.
3. 팀원에게 "현업에 물어봤습니다"라고 알리고, 답을 기다리는 동안 STEP 3부터 계속합니다.
4. 강사(총무팀)가 같은 이슈에 `[현업 확인 결과]` 댓글을 남기면, PO가 읽고 팀원에게 결과를 알립니다. 강사가 되물으면(예: "Copilot은 뭐라고 추천했나요? 근거는요?") 댓글로 답합니다.

확인: 결정 이슈에 내 질문 댓글과 총무팀의 `[현업 확인 결과]` 댓글이 있습니다.

!!! info "콜라보레이터가 아니어도 댓글을 달 수 있어요"
    팀 리포지토리는 Public이라 GitHub 계정이 있으면 누구나 이슈에 댓글을 달 수 있습니다. 그래서 강사를 협업자로 초대하지 않아도 멘션으로 묻고 답을 받을 수 있습니다. 담당자(Assignees)로 지정하는 것은 협업자만 됩니다.

!!! warning "Copilot의 결정안은 결정이 아닙니다"
    Copilot이 "4시간을 추천합니다"라고 써도 그것은 초안입니다. 회의록에 없는 정책을 Copilot이 정한 대로 구현하면, 현업이 원하지 않은 기능이 들어갑니다. 이것이 7교시에 다룰 **환각**과 **책임 있는 사용**의 시작점입니다.

## STEP 3. (PM) 라벨과 이슈 S1~S4 만들기

1. github.com 팀 리포지토리 → **Issues** 탭 → **Labels**(라벨)를 클릭합니다.
2. **New label**(새 라벨)을 클릭하고 **Label name**에 입력한 뒤 **Create label**을 클릭합니다.

    ```text
    스토리
    ```

3. **Issues** 탭 → **New issue**를 클릭합니다.
4. 제목과 본문을 입력합니다. 첫 번째 S1 예시입니다.

    ```text
    [S1] 같은 회의실, 같은 날짜에 시간이 겹치는 예약을 막는다
    ```

    ```text
    ## 스토리
    총무 담당자로서, 같은 회의실 같은 날짜에 시간이 겹치는 예약을 막고 싶다. 회의실 앞에서 다투는 일을 없애기 위해서다.

    ## 바꿀 곳
    booking/rules.py

    ## 완료 기준
    10:00~11:00이 있으면 10:30~11:30은 "이미 예약된 시간"으로 실패. 11:00~12:00은 성공(맞닿음은 겹침 아님)

    ## 인수 조건
    (BA가 채웁니다)
    ```

5. 오른쪽 **Labels** 톱니 → `스토리`를 고릅니다.
6. 오른쪽 **Assignees** 톱니 → 이 스토리를 맡을 팀원을 고릅니다. 빈 곳을 클릭해 닫습니다.
7. **Create**(화면에 따라 **Submit new issue**)를 클릭합니다.
8. S2, S3, S4도 [팀 백로그](index.md#backlog) 표를 보고 같은 방법으로 만듭니다. 3인 팀은 S4를 만들지 않습니다.

    | 이슈 제목 |
    |---|
    | `[S2] 회의실 정원을 넘는 예약을 막는다` |
    | `[S3] 예약을 취소할 수 있다` |
    | `[S4] 18:00에 끝나는 예약이 되게 고친다` |

9. 팀에 이슈 번호와 담당자를 말로 알립니다. 예: "S1은 #2 김○○, S2는 #3 ..."

??? tip "Copilot에게 이슈 초안을 한 번에 만들게 할 수도 있어요 (미리 보기 기능)"
    github.com의 Copilot은 이슈 초안을 만들어 줍니다. 제목, 본문, 라벨, 담당자까지 채운 초안을 보여 주고, 사람이 검토한 뒤 **Create**를 눌러야 등록됩니다. 여러 개를 한 번에 부탁하면 이슈마다 따로 초안을 만듭니다. 라벨을 새로 만들어 주는지는 문서에 없으니, 위 1~2번으로 `스토리` 라벨은 먼저 만들어 둡니다.

    1. 브라우저에서 `github.com/copilot`을 엽니다.
    2. 아래를 붙여 넣고 `<PO아이디>`, `<번호>`, 담당자 아이디를 바꿉니다.

        ```text
        In <PO아이디>/room-booking-team<번호>, 아래 스토리 4개로 이슈 4개를 만들어 주세요.
        각 이슈 본문은 "## 스토리", "## 바꿀 곳", "## 완료 기준", "## 인수 조건(BA가 채웁니다)"으로 쓰고, 라벨은 스토리로 붙여 주세요.
        1) [S1] 같은 회의실, 같은 날짜에 시간이 겹치는 예약을 막는다 / booking/rules.py / 담당: 아이디1
        2) [S2] 회의실 정원을 넘는 예약을 막는다 / booking/rules.py / 담당: 아이디2
        3) [S3] 예약을 취소할 수 있다 / booking/service.py, booking/__main__.py / 담당: 아이디3
        4) [S4] 18:00에 끝나는 예약이 되게 고친다 / booking/rules.py / 담당: 아이디4
        완료 기준은 팀 백로그의 확인 방법을 그대로 쓰고, 문서에 없는 정책은 넣지 마세요.
        ```

    3. 초안마다 제목, 본문, 라벨, 담당자를 읽고 고친 뒤 **Create**를 누릅니다. 문서에 없는 정책이 들어갔으면 지웁니다.

    미리 보기 기능이라 화면이 바뀌거나 계정에 따라 보이지 않을 수 있습니다. 그때는 위 3~8번처럼 직접 만듭니다.

확인: **Issues** 탭에 `스토리` 라벨이 붙은 이슈가 4개(3인 팀 3개) 있고, 각각 담당자가 **1명씩**, 팀원 모두가 하나씩 맡았습니다.

!!! tip "누가 무엇을 맡을까요?"
    오전에 개인 리포지토리에서 S1(겹침), S4(18시)를 해 봤습니다. 처음 해 보는 S2(정원), S3(취소)는 자신 있는 사람이 맡으면 좋습니다. 이슈 본문 초안은 [역할 카드](index.md#role-cards)의 PM 예시 프롬프트로 Copilot에게 만들게 해도 됩니다.

!!! note "이슈 번호는 팀마다 다릅니다"
    PO의 결정 이슈가 먼저 만들어졌다면 S1은 `#2`부터 시작합니다. 이 가이드는 이슈 번호를 `<번호>`로 씁니다. 내 이슈의 실제 번호로 바꿔 읽습니다.

## STEP 4. (BA) 인수 조건 초안 만들고 검토해서 붙이기

1. VS Code Chat 보기에서 **+**(**New Chat**)를 클릭합니다. Session Target **Copilot**, Agent **Ask**를 고릅니다.
2. **+**(**Add Context**) → **Files & Folders**로 `docs/00_현업요청.md`, `docs/02_현행_업무.md`를 추가합니다.
3. Chat에 붙여 넣기. 스토리 줄과 완료 기준은 해당 이슈에서 복사해 바꿉니다.

    ```text
    아래 스토리의 인수 조건을 Given-When-Then 형식으로 3개 써 주세요.
    - 정상 동작 1개, 실패 동작 1개, 경계값 1개를 넣어 주세요.
    - 실제로 실행해 볼 수 있게 회의실 ID, 날짜, 시간, 인원을 구체적으로 써 주세요.
    - 첨부 문서에 없는 정책은 만들지 말고 "확인 필요"로 표시해 주세요.

    스토리: [S1] 같은 회의실, 같은 날짜에 시간이 겹치는 예약을 막는다
    완료 기준: 10:00~11:00이 있으면 10:30~11:30은 "이미 예약된 시간"으로 실패. 11:00~12:00은 성공(맞닿음은 겹침 아님)
    ```

4. 답을 사람이 검토합니다.

    | 검토 기준 | 확인 |
    |---|---|
    | 완료 기준과 같은 숫자인가 | 10:30~11:30 실패, 11:00~12:00 성공 같은 값이 그대로인가 |
    | 실행해 볼 수 있는가 | 회의실 ID, 날짜, 시간이 구체적인가 |
    | 지어낸 정책이 없는가 | 최대 시간, 노쇼, 알림 같은 범위 밖 내용이 없는가 |

5. github.com에서 해당 이슈를 엽니다. 본문 오른쪽 위 **...** → **Edit**를 클릭합니다.
6. `## 인수 조건` 아래 `(BA가 채웁니다)`를 지우고 검토한 인수 조건을 붙여 넣은 뒤 **Save**(화면에 따라 **Update comment**)를 클릭합니다.
7. S2, S3, S4도 반복합니다. 같은 채팅에서 스토리와 완료 기준만 바꿔 보냅니다.

확인: 스토리 이슈 본문에 Given-When-Then 인수 조건이 3개씩 있습니다. 시간이 모자라면 완료 기준을 기본으로 삼고, 빠진 경우만 인수 조건으로 보완합니다. 다른 팀원은 BA를 기다리지 않고 미션 5-2를 시작합니다.

## STEP 5. (개발자) 바꿀 파일과 충돌 위험 분석하기

1. VS Code Chat 보기에서 **+**(**New Chat**)를 클릭합니다. Session Target **Copilot**, Agent **Ask**를 고릅니다.
2. Chat에 붙여 넣기

    ```text
    #codebase 이 리포지토리에서 아래 스토리 4개를 각각 다른 사람이 동시에 구현합니다.
    S1 겹치는 예약 막기 / S2 정원 초과 막기 / S3 예약 취소(python -m booking cancel --id) / S4 18:00에 끝나는 예약 허용

    1. 스토리마다 바뀔 파일과 함수를 표로 정리해 주세요. 테스트 파일도 포함해 주세요.
    2. 같은 파일, 같은 함수를 동시에 고쳐 병합 충돌이 날 수 있는 조합을 알려 주세요.
    3. 충돌을 줄이는 병합 순서를 추천해 주세요.
    ```

3. 답을 검토합니다. 아래와 비슷하면 됩니다.
    - S1, S2, S4가 모두 `booking/rules.py`의 `validate()`와 `tests/test_rules.py`를 바꿉니다.
    - S3는 `booking/service.py`, `booking/__main__.py`를 바꿔 다른 스토리와 겹치지 않습니다.
4. 각 스토리 이슈에 해당 내용을 댓글로 남깁니다. 예: S1 이슈에

    ```text
    [개발자 분석] 바뀔 파일: booking/rules.py validate(), tests/test_rules.py
    충돌 위험: S2, S4와 같은 함수와 테스트 파일을 고칩니다. 6교시에 병합 순서를 PM과 정하고, 충돌 나면 같이 풉니다.
    ```

5. PM에게 추천 병합 순서를 알려 줍니다.

확인: 모든 스토리 이슈에 `[개발자 분석]` 댓글이 있습니다.

## STEP 6. (모두) 내 이슈 읽기

1. **Issues** 탭 → 내 이름이 담당자인 이슈를 엽니다.
2. 스토리, 완료 기준, 인수 조건, 개발자 분석을 읽습니다.
3. 이해가 안 되는 것은 이슈 댓글로 BA나 개발자를 `@아이디`로 멘션해 묻습니다.
4. 이슈 번호를 메모합니다. 미션 5-2에서 브랜치 이름이 됩니다.

확인: 내 이슈 번호를 알고, 인수 조건을 내 말로 설명할 수 있습니다.

## 다 됐는지 확인

- [ ] (PO) 결정 이슈에 우선순위, `@skilleat-labs` 질문 댓글, `[현업 확인 결과]` 답변이 있다
- [ ] (PM) 라벨 `스토리`가 붙은 이슈 S1~S4(3인 팀 S1~S3)가 있고 담당자가 1명씩이다
- [ ] (BA) 모든 스토리 이슈에 인수 조건이 있다
- [ ] (개발자) 모든 스토리 이슈에 `[개발자 분석]` 댓글이 있다
- [ ] (모두) 내 이슈 번호를 안다

## 막히면

!!! tip "먼저 Copilot과 함께 해결합니다"
    오류 메시지나 막힌 상황을 Chat(Ask)에 붙여 넣고 원인과 해결 순서를 묻습니다. 아래는 자주 막히는 경우입니다. 묻는 방법은 [막혔을 때](../setup/3-troubleshooting.md#copilot)에 있습니다.

??? failure "Assignees 목록에 팀원 이름이 없어요"
    팀원이 미션 5-0의 초대를 아직 수락하지 않은 것입니다. PO가 **Settings** → **Collaborators**에서 상태를 보고, 팀원은 초대 주소에서 **Accept invitation**을 누릅니다.

??? failure "Copilot이 첨부한 문서를 읽지 않고 일반적인 답을 해요"
    입력 칸 위에 첨부한 파일 이름이 보이는지 확인합니다. 안 보이면 다시 **+**(**Add Context**)로 추가하거나, 탐색기에서 파일을 입력 칸으로 끌어다 놓습니다.

??? failure "`#codebase`를 쳤는데 목록에 안 나와요"
    `#`만 먼저 치고 잠시 기다리면 맥락 항목 목록이 뜹니다. 거기서 `codebase`를 고릅니다.

??? failure "인수 조건에 노쇼 자동 취소나 알림이 들어 있어요"
    Copilot이 범위 밖 내용을 넣은 것입니다. 지우고 붙입니다. 회의록의 "이번 범위가 아닌 것"과 PO의 `[현업 확인 결과]`를 기준으로 봅니다.

??? failure "이슈 본문의 Edit 메뉴를 못 찾겠어요"
    이슈 본문 상자 오른쪽 위 **...**(점 3개)을 누르면 **Edit**가 있습니다. 내가 만든 이슈가 아니어도 Write 권한이 있으면 고칠 수 있습니다.
