## 교안 { #lecture }

### 에이전트는 스스로 고치고, 실행하고, 확인합니다

에이전트는 일을 맡기면 스스로 계획을 세우고, 필요한 파일을 찾아 고치고, 테스트 같은 명령을 실행해서 결과를 확인해요. 테스트가 실패하면 원인을 보고 다시 고쳐요. 사람으로 치면 일을 받아서 끝까지 해 오는 동료예요. 하지만 동료가 해 온 일도 검토하듯이, 에이전트가 한 일도 우리가 검토해야 해요.

### 브랜치는 main을 건드리지 않고 따로 고치는 작업 공간입니다

1교시에 본 브랜치를 이제 직접 만들어요. 브랜치는 지금 있는 브랜치에서 갈라져 나온 작업 공간이에요. 그림처럼 main에서 overlap-check를 갈라 만들고, 거기서 c3, c4처럼 커밋해요. 이렇게 아무리 고쳐도 main은 그대로예요.

왜 이렇게 할까요. 첫째, main은 늘 동작하는 상태로 지킬 수 있어요. 둘째, 사람마다 기능마다 브랜치를 따로 만들어 동시에 일할 수 있어요. 오후에 팀원 넷이 각자 story 브랜치에서 일하는 것도 이 덕분이에요. 셋째, 합치기 전에 PR에서 리뷰와 자동 테스트를 거쳐요. 넷째, 잘못되면 브랜치만 버리면 돼요. 그래서 4-1에서 브랜치를 만들기 전에 상태 표시줄 브랜치 이름이 main인지 먼저 봐요.

### 큰 일은 /plan 으로 계획부터 받습니다

```text
/plan 현업 요청 1번 '겹치는 예약 막기'를 구현하려고 해.
#codebase 와 docs/00_현업요청.md 를 근거로, 바꿀 파일과 테스트 계획을 세워 줘.
```

큰 작업은 바로 고치게 하지 말고 /plan으로 계획부터 받아요. 계획을 보면 Copilot이 요구를 제대로 이해했는지 미리 알 수 있어요. 겹침 검사라면 세 가지를 봐요. 같은 회의실, 같은 날짜끼리만 비교하는지, 10시에서 11시 예약 다음에 11시에서 12시 예약은 맞닿을 뿐 겹치는 게 아니라는 걸 아는지, 그리고 테스트에 이런 경우가 다 들어 있는지예요. 계획이 틀렸으면 지금 고치는 게 가장 싸요.

### 권한은 Manual: 승인 요청이 뜨면 읽고 판단합니다

오늘 권한은 Manual이에요. 자동 승인되지 않은 작업은 승인 요청이 떠요. 이미 허용한 작업이나 읽기 전용 명령은 묻지 않고 지나갈 수 있어요. 승인 요청이 뜨면 무작정 다 승인하지 말고 무엇을 하려는지 읽어요. python -m pytest처럼 테스트를 돌리는 건 승인해도 돼요. 반대로 파일을 지우는 rm이나 del, 무언가를 설치하거나 밖으로 보내는 명령은 멈추고 확인해요. 모르겠으면 Stop을 누르고 물어보세요. 문서 기준으로 rm, del 같은 위험한 명령은 승인이 필요해요.

### 바뀐 것은 채팅과 소스 제어에서 검토하고, 아니면 되돌립니다

에이전트가 일을 마치면 채팅에 바뀐 파일과 몇 줄이 바뀌었는지가 보여요. 채팅에서 눌러서 보거나, 소스 제어 보기를 열어 Changes 목록에서 파일을 눌러 검토해요. 특정 부분이 마음에 안 들면 diff에서 그 부분을 선택하고 고칠 점을 말하면 돼요. 아예 처음부터 다시 하고 싶으면 이전 요청에 마우스를 올려 Restore Checkpoint를 눌러요. 파일과 채팅이 그 시점으로 돌아가요. 단, 이미 실행한 터미널 명령이나 외부로 보낸 것까지 되돌리지는 않아요.

### 테스트는 경계에서 틀립니다

기존 예약이 10:00~11:00일 때:

| 새 예약 | 결과 | 이유 |
|---|---|---|
| 10:30~11:30 | 실패 | 겹침 |
| 11:00~12:00 | 성공 | 끝과 시작이 맞닿을 뿐 겹치지 않음 |

| 테스트의 부분 | 확인할 질문 |
|---|---|
| 입력 준비 | 어떤 방, 날짜, 시간, 인원을 넣었나요? |
| 함수 실행 | 어떤 기능을 실행했나요? |
| `assert` | 무엇이 나오면 맞다고 판단하나요? 인수 조건과 같나요? |

버그는 대부분 경계에서 생겨요. 10시에서 11시 예약이 있을 때 10시 반 시작은 당연히 겹치지만, 11시 시작은 끝과 시작이 맞닿을 뿐 겹치지 않아요. 부등호 하나를 잘못 쓰면 11시 예약까지 막혀요. 2교시에 고친 18시 버그도 같은 종류였죠. 그래서 테스트는 이런 경계를 꼭 넣어요. /tests로 Copilot에게 경계값 테스트를 더 만들어 달라고 할 수 있어요. 하지만 어떤 경우를 테스트할지 정하고, 그 테스트가 정말 맞는 내용인지 읽는 건 사람의 몫이에요. 테스트는 세 부분만 보면 돼요. 어떤 입력을 준비했는지, 어떤 기능을 실행했는지, assert에서 무엇이 나오면 맞다고 보는지예요. 기대값 자체가 인수 조건과 맞는지도 확인하고, 테스트를 지워서 통과시킨 건 아닌지도 봐요.

### PR을 열면 테스트가 자동으로 돕니다

고친 걸 커밋하고 push한 다음 github.com에서 PR을 열어요. PR 설명은 Copilot 메뉴의 Summary로 자동 요약을 받을 수 있어요. PR이 열리면 Starter에 들어 있는 테스트 워크플로가 자동으로 돌아요. 초록 체크면 병합하고, 빨간 X면 Details에서 어떤 테스트가 실패했는지 보고 그 내용을 Copilot에게 붙여서 고쳐요. 이게 1교시에 말한 CI예요.

### PR 다음에는 리뷰, 고치기, 병합, 정리가 이어집니다

| 순서 | 누가 | 무엇을 | 어디서 |
|---|---|---|---|
| ① PR 열기 | 작성자 | 무엇을 왜 바꿨는지, Closes #번호 | github.com |
| ② 리뷰 | 다른 팀원 | Comment, Approve, Request changes 중 하나 | Files changed → Review changes |
| ③ 고치기 | 작성자 | 같은 브랜치에 커밋, Sync Changes. 새 PR 아님 | VS Code |
| ④ 병합 | 병합 담당 | 테스트 초록, 승인 확인 후 Merge | github.com |
| ⑤ 정리 | 모두 | main으로 돌아와 Pull, 다 쓴 브랜치 삭제 | VS Code, github.com |

| 리뷰 종류 | 뜻 |
|---|---|
| Comment | 의견만 남김 |
| Approve | 병합해도 됨 |
| Request changes | 병합 전에 고칠 점이 있음 |

PR을 열었다고 끝이 아니에요. 다른 팀원이 Files changed에서 Review changes를 눌러 리뷰해요. 리뷰는 세 종류예요. 의견만 남기는 Comment, 병합해도 된다는 Approve, 고칠 점이 있다는 Request changes예요. 작성자는 자기 PR을 승인할 수 없어요. 고칠 점을 받으면 새 PR을 열지 않고 같은 브랜치에 커밋해서 Sync Changes를 누르면 같은 PR에 이어 붙어요. 테스트가 초록이고 승인이 나면 병합하고, 모두 main으로 돌아와 Pull해서 최신으로 맞추고 다 쓴 브랜치는 지워요. 오전 4-3은 혼자라서 리뷰 없이 병합하지만, 오후에는 팀원이 이 순서대로 리뷰해요.

### 병합 방법은 세 가지입니다

| 방법 | main에 남는 기록 |
|---|---|
| Create a merge commit (기본) | 브랜치 커밋이 모두 남고 병합 커밋 M이 하나 더. 오늘은 이것 |
| Squash and merge | PR의 커밋을 커밋 하나(S)로 합침 |
| Rebase and merge | 병합 커밋 없이 커밋을 main 끝에 일렬로 |

PR 병합 버튼 옆 화살표를 누르면 병합 방법이 세 가지 보여요. 셋 다 코드는 똑같이 main에 들어가고, main에 기록이 남는 모양만 달라요. 기본인 Create a merge commit은 브랜치의 커밋이 모두 남고 병합 커밋이 하나 더 생겨요. 오늘은 이걸 써요. Squash and merge는 PR의 커밋을 하나로 합쳐서 main 기록이 깔끔해요. Rebase and merge는 병합 커밋 없이 커밋을 main 끝에 일렬로 붙여요. 어떤 방법을 쓸지는 팀이 정하고, 리포지토리 설정에서 보이는 방법을 제한할 수도 있어요.
