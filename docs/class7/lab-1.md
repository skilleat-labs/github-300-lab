# 실습 7-1. 클라우드 에이전트에 이슈 맡기기

!!! abstract "이 실습에서 할 일"
    - PM이 리팩터링 이슈를 쓰고 **Assignees**에 **Copilot**을 지정해 클라우드 에이전트에게 맡깁니다.
    - 클라우드 에이전트가 GitHub에서 작업해 PR을 엽니다.
    - 팀이 PR을 검토(테스트 통과, 동작이 그대로인지)하고 병합 여부를 결정합니다.

**소요 시간** 이슈 맡기기 약 5분 (에이전트 작업 시간 별도, 수업 안에 끝나지 않아도 됩니다)  **실습 장소** 팀 리포지토리 `room-booking-team<번호>` (github.com)  **관련 교안** [7교시 교안](index.md)

## 준비

!!! warning "팀당 1건만 맡깁니다"
    클라우드 에이전트는 AI Credits와 GitHub Actions 사용 시간을 씁니다. **팀당 이슈 1건만** 맡깁니다. 팀원이 각자 맡기지 않습니다.

- 이 실습은 PM 한 명이 이슈를 쓰고, 나머지는 같이 화면을 보며 검토합니다. 3인 팀은 PO가 합니다.

!!! info "클라우드 에이전트와 VS Code의 Agent는 무엇이 다른가요?"
    VS Code의 Agent는 **내 PC**에서 내가 지켜보며 승인하고 일합니다. 클라우드 에이전트는 **GitHub 쪽**에서 혼자 일하고, 끝나면 항상 PR을 엽니다. 내 PC를 꺼도 일이 진행됩니다. 결과는 PR로 받으니, 오늘 해 온 PR 검토를 그대로 하면 됩니다.

## STEP 1. 지금 동작 기록해 두기

리팩터링(refactoring)은 동작은 그대로 두고 코드를 읽기 쉽게 고치는 것입니다. "그대로인지" 확인하려면 지금 결과를 먼저 적어 둡니다.

1. VS Code에서 팀 리포지토리를 열고 main을 최신으로 맞춥니다.
2. 터미널에서 실행합니다.

    ```text
    python -m booking report
    ```

    Starter 데이터 그대로라면 이렇게 나옵니다. 우리 팀이 데이터를 바꿨다면 다를 수 있습니다.

    ```text
    소회의실 A {'건수': 2, '시간': 2.5, '이용률': '보통'}
    소회의실 B {'건수': 1, '시간': 1.0, '이용률': '낮음'}
    중회의실 {'건수': 1, '시간': 2.0, '이용률': '낮음'}
    대회의실 {'건수': 1, '시간': 2.0, '이용률': '낮음'}
    ```

3. 결과를 메모장에 복사해 둡니다.
4. `booking/report.py`를 열어 봅니다. 중첩된 `if`와 `t`, `c`, `a`, `b`, `lv` 같은 한 글자 변수가 보입니다.

확인: `report` 결과를 메모해 두었습니다.

## STEP 2. (PM) 이슈 쓰고 Copilot에게 맡기기

1. github.com 팀 리포지토리 → **Issues** → **New issue**를 클릭합니다.
2. 제목과 본문을 입력합니다.

    ```text
    report.py를 읽기 쉽게 리팩터링하고 테스트 추가 (동작은 그대로)
    ```

    ```text
    ## 배경
    booking/report.py의 usage_report()는 중첩 if와 한 글자 변수(t, c, a, b, lv)가 많아 읽기 어렵습니다.

    ## 할 일
    - 변수 이름을 뜻이 드러나게 바꾸고, 중첩 if를 줄여 주세요.
    - 시간 계산은 booking/rules.py의 to_minutes()를 재사용할 수 있으면 써 주세요.
    - tests/test_report.py에 usage_report() 테스트를 추가해 주세요. 건수, 시간, 이용률(없음, 낮음, 보통, 높음)을 확인해 주세요.

    ## 지켜야 할 것
    - 동작은 바꾸지 않습니다. python -m booking report 출력이 지금과 같아야 합니다.
    - 다른 파일의 동작은 바꾸지 않습니다.
    - 기존 테스트는 모두 통과해야 합니다.
    ```

3. 오른쪽 **Assignees** 톱니 → 목록에서 **Copilot**을 고릅니다.
4. **Create**(화면에 따라 **Submit new issue**)를 클릭합니다.

확인: 이슈의 **Assignees**에 **Copilot**이 보입니다.

!!! note "화면이 조금 다를 수 있어요"
    이슈의 **Assignees**에서 **Copilot**을 지정하는 방법은 공식 문서 검색 요약으로 확인한 것입니다. 목록에 Copilot이 없으면 강사에게 알립니다. 리포지토리의 **Agents** 탭도 github.com에서 Copilot을 쓰는 입구입니다.

!!! tip "이슈를 잘 쓰는 것이 프롬프트입니다"
    클라우드 에이전트는 이슈 본문을 보고 일합니다. 3교시에 배운 좋은 프롬프트 구조(배경, 할 일, 지켜야 할 것, 확인 방법)가 그대로 이슈 본문이 됩니다.

## STEP 3. 맡겨 두고 다른 실습하기

클라우드 에이전트는 작업에 몇 분에서 십여 분이 걸립니다.

1. 기다리지 않습니다. 바로 [실습 7-2](lab-2.md)를 진행하고, 이어서 [실습 7-3](lab-3.md)을 합니다.
2. 가끔 **Pull requests** 탭을 봅니다. Copilot이 연 PR이 생기면 엽니다.
3. PR의 **Conversation** 탭에서 Copilot이 쓴 작업 설명을 읽습니다.

확인: Copilot이 연 PR이 있고, 이슈와 연결되어 있습니다.

## STEP 4. (팀 함께) PR 검토하기

Copilot은 작업을 마치면 리뷰를 요청합니다. 알림이나 PR 화면에서 확인합니다. 아래 순서를 지킵니다.

1. **Files changed**를 **먼저** 읽습니다. 바뀐 파일이 `booking/report.py`와 테스트 파일 정도인지 봅니다. `.github/workflows/`를 바꿨으면 특히 주의합니다.
2. 이상이 없으면 쓰기 권한이 있는 사람이 PR 병합 영역의 **Approve and run workflows**를 클릭합니다. 기본 설정에서는 Copilot이 올린 변경에 워크플로가 자동으로 돌지 않으니, 이 버튼 없이 기다려도 검사가 시작되지 않습니다.
3. **Checks**에서 **테스트 / test**가 초록인지 봅니다.
4. 변수 이름이 읽기 쉬워졌는지 팀이 같이 읽어 봅니다.
5. 동작이 같은지 직접 비교합니다. VS Code에서
    1. 소스 제어의 동기화 아이콘을 누르거나 명령 팔레트에서 `Git: Fetch`를 실행합니다.
    2. 상태 표시줄 브랜치 이름 클릭 → PR 위쪽에 보이는 Copilot 브랜치 이름(`origin/`으로 시작)을 고릅니다.
    3. 실행합니다.

        ```text
        python -m booking report
        ```

        ```text
        python -m pytest
        ```

    4. STEP 1에서 메모한 결과와 한 글자씩 비교합니다.
    5. 끝나면 상태 표시줄에서 다시 `main`으로 돌아옵니다.

확인: 테스트가 통과하고, `report` 출력이 STEP 1과 같습니다.

## STEP 5. 병합 여부 결정하기

| 검토 결과 | 결정 |
|---|---|
| 테스트 통과, 출력 같음, 읽기 쉬워짐 | Draft이면 **Ready for review**를 클릭하고, BA가 **Approve**, PM이 병합 |
| 출력이 다름 | 병합하지 않음. PR에 무엇이 다른지 댓글로 남김 |
| 범위 밖 파일을 바꿈 | 병합하지 않음. 이유를 댓글로 남김 |

확인: 팀이 병합하거나, 병합하지 않는 이유를 PR 댓글로 남겼습니다.

!!! warning "사람이 해야 하는 일"
    Copilot은 자기 PR을 **Ready for review**로 바꾸거나 승인, 병합할 수 없습니다. 그리고 Copilot에게 일을 맡긴 사람(PM)은 그 PR을 승인할 수 없습니다. 그래서 BA나 PO가 승인합니다. 고칠 점이 있으면 PR 댓글에 `@copilot`을 붙여 요청합니다.

!!! tip "시간 안에 안 끝나면"
    PR이 열린 것까지만 확인하고 7-3으로 넘어갑니다. 검토와 병합은 다음 날 해도 됩니다. 일을 맡겨 두고 다른 일을 하는 것이 클라우드 에이전트를 쓰는 이유입니다.

## 다 됐는지 확인

- [ ] `report` 결과를 미리 메모했다
- [ ] (PM) 이슈를 쓰고 Assignees에 Copilot을 지정했다 (팀당 1건)
- [ ] 변경을 먼저 읽고 **Approve and run workflows**를 눌렀다 (또는 다음 날 하기로 했다)
- [ ] 테스트 통과와 `report` 출력이 같은지 확인했다 (또는 다음 날 확인하기로 했다)
- [ ] 병합 여부를 팀이 결정했다

## 막히면

??? failure "Assignees 목록에 Copilot이 없어요"
    이슈를 만든 사람의 Copilot 플랜을 봅니다. 클라우드 에이전트는 Pro에 포함되지만 Free에는 없습니다. 리포지토리 소유자(PO)가 Pro인지 확인하고, PO가 지정해 봅니다.

??? failure "한참 기다려도 PR이 안 열려요"
    클라우드 에이전트는 시간이 걸릴 수 있습니다. 7-3을 먼저 하고 돌아옵니다. 수업이 끝날 때까지 안 열리면 다음 날 확인합니다.

??? failure "PR이 열렸는데 테스트가 돌지 않아요"
    정상입니다. 변경 내용을 읽은 뒤 PR 병합 영역의 **Approve and run workflows**를 누릅니다.

??? failure "병합 버튼이 안 눌려요"
    Draft 상태입니다. **Ready for review**를 먼저 누릅니다. 승인은 일을 맡긴 사람이 아닌 팀원이 합니다.

??? failure "테스트가 실패한 PR이 열렸어요"
    병합하지 않습니다. **Details** 로그의 실패 줄을 PR 댓글에 남깁니다. 이것도 검토의 결과입니다.

??? failure "Copilot 브랜치로 바꿨더니 report 결과가 달라요"
    동작이 바뀐 것입니다. 어떤 줄이 다른지 PR 댓글로 남기고 병합하지 않습니다. 이용률 경계값(2시간, 6시간)에서 `>`와 `>=`가 바뀐 경우가 많습니다.

??? failure "브랜치 목록에 Copilot 브랜치가 없어요"
    아직 가져오지 않은 것입니다. 명령 팔레트에서 `Git: Fetch`를 실행하고 다시 봅니다.
