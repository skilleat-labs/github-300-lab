## 교안 { #lecture }

### 좋은 프롬프트는 목표, 맥락, 형식, 제약을 담습니다

이렇게 쓰면 Copilot이 범위와 형식을 마음대로 정합니다.

```text
회의록 보고 사용자 스토리 만들어 줘
```

이렇게 쓰면 더 좋습니다.

```text
[목표] 회의록의 '결정한 것' 4개를 사용자 스토리로 만들어 줘.
[맥락] docs/01_킥오프_회의록.md, 사용자는 회의실을 예약하는 직원과 총무팀이야.
[형식] 스토리마다 '누구로서, 무엇을, 왜' 한 줄 + 인수 조건 2개, 표로.
[제약] 회의록에 없는 정책은 정하지 말고 '확인 필요'로 표시해.
```

!!! info "사용자 스토리와 인수 조건이 뭔가요?"
    **사용자 스토리**는 기능 요구를 사용자 입장에서 한 문장으로 쓴 것입니다. 형식은 "〈누구〉로서, 〈무엇〉을 원한다. 왜냐하면 〈이유〉이기 때문이다."입니다.

    | 회의록의 결정 | 사용자 스토리로 바꾸면 |
    |---|---|
    | 겹치는 예약을 막는다 | 회의실을 예약하는 **직원으로서**, 이미 예약된 시간에는 **예약이 안 되기를 원한다**. 회의실 앞에서 누가 먼저 예약했는지 **다투지 않기 위해서**이다. |

    **인수 조건**은 그 스토리가 다 됐는지 판단하는 기준입니다. 확인할 수 있는 예로 씁니다.

    - 10:00~11:00 예약이 있으면 10:30~11:30은 "이미 예약된 시간"으로 실패
    - 11:00~12:00은 성공 (끝과 시작이 맞닿는 것은 겹침이 아님)

    "겹침 검사 구현"이라고만 쓰면 누구를 위한 일인지, 어디까지 하면 끝인지가 빠집니다. 스토리와 인수 조건으로 쓰면 만드는 사람과 검토하는 사람이 같은 기준으로 확인합니다.

    **스토리 하나가 GitHub 이슈 하나가 됩니다.** 오후에는 이렇게 이어집니다.

    | 언제 | 무엇 |
    |---|---|
    | 3-1 | 회의록의 결정 4개를 스토리 4개로 씁니다 |
    | 5-1 | PM이 스토리를 이슈 S1~S4로 등록합니다. 본문에 스토리 한 줄과 인수 조건이 들어갑니다 |
    | 5-2 | 각자 이슈 하나를 맡아 `story-번호` 브랜치에서 구현합니다 |
    | 6-1 | PR에 `Closes #번호`를 쓰고, BA가 인수 조건으로 검토해 병합하면 이슈가 닫힙니다 |

    이슈가 모두 스토리는 아닙니다. 버그 신고, 변경 요청(CR-001), 배포 설정 같은 작업도 이슈로 만듭니다. 그중 사용자 입장의 기능 요구를 쓴 것이 스토리입니다.

같은 일을 시켜도 프롬프트에 따라 결과가 크게 달라져요. '회의록 보고 스토리 만들어 줘'라고만 하면 Copilot이 범위도 형식도 마음대로 정해요. 네 가지를 담아 보세요. 무엇을 원하는지 목표, 어떤 자료를 보고 누구를 위한 것인지 맥락, 어떤 모양으로 받고 싶은지 형식, 하지 말아야 할 것 같은 제약이에요. 특히 제약의 '회의록에 없는 정책은 정하지 말고 확인 필요로 표시해'가 오늘 아주 중요해요.

### GitHub 문서가 권하는 프롬프트 전략

| 전략 | 뜻 | 오늘 예 |
|---|---|---|
| Start general, then get specific | 넓게 시작해 구체적으로 | 목표 한 줄 → 조건 추가 |
| Give examples | 예시를 준다 | 스토리 예시 1개 (few-shot) |
| Break complex tasks | 큰 일은 쪼갠다 | 계획 → 구현 → 테스트 |
| Avoid ambiguity | 모호함을 피한다 | '그거' 대신 파일, 함수 이름 |
| Provide relevant context | 관련 맥락을 준다 | 회의록 첨부, #codebase |
| Keep history relevant | 대화 기록을 관련 있게 | 주제가 바뀌면 새 채팅 |
| Review Copilot's output | 결과를 검토한다 | 실행, 근거, 테스트 |

GitHub 문서 'Prompt engineering for GitHub Copilot Chat'에 나오는 전략들이에요. 문서에는 아홉 개가 있는데 오늘 쓰는 일곱 개만 골랐어요. 넓게 시작해서 구체적으로 좁히고, 예시를 주고, 큰 일은 쪼개고, '그거' 같은 모호한 말 대신 파일 이름을 쓰고, 관련 맥락을 붙이고, 주제가 바뀌면 새 채팅을 열고, 결과는 꼭 검토해요. 나머지 둘은 '실험하고 반복하기'와 '좋은 코드 습관 따르기'예요.

### 예시를 주면 원하는 모양으로 답합니다: zero-shot과 few-shot

예시 없이 요청하는 걸 zero-shot, 예시를 몇 개 함께 주는 걸 few-shot이라고 해요. GH-300 시험 범위에도 있는 용어예요. 예시가 없으면 Copilot이 형식을 마음대로 정해서 매번 모양이 달라져요. '이런 모양으로 써 줘' 하고 스토리 예시 하나만 붙여도 형식, 말투, 길이가 맞춰져요. 3-1에서 두 가지를 직접 비교해 봐요.

### 맥락에 없는 결정을 Copilot이 채워 넣을 수 있습니다

회의록에는 결정하지 못한 것이 세 개 있어요. 최대 예약 시간, 노쇼 자동 취소 기준, 현황판 연락처 공개예요. 그런데 Copilot에게 스토리를 만들어 달라고 하면, 이걸 '최대 2시간까지'처럼 그럴듯하게 정해 버리는 경우가 많아요. 이렇게 사실이 아닌 걸 그럴듯하게 만드는 걸 환각이라고 해요. 기획 문서에서 이게 제일 위험해요. 아무도 결정하지 않은 정책이 요구사항이 돼 버리니까요. 대책은 프롬프트 제약에 '정하지 말고 확인 필요로 표시해'를 넣고, 결과를 회의록과 대조하는 거예요.

### 지침 파일: 매번 하는 말을 파일 하나로

```text title=".github/copilot-instructions.md"
# 회의실 예약 서비스 지침

- 답변은 한국어로 한다.
- 오류 메시지는 한국어 문장으로 쓴다.
- 기능을 바꾸면 tests/에 pytest 테스트를 추가한다.
- 회의록에 없는 정책은 정하지 말고 질문한다.
- data/reservations.json은 요청할 때만 바꾼다.
```

매번 '한국어로 답해 줘, 테스트도 추가해 줘'라고 반복하지 않으려면 지침 파일을 만들어요. 리포지토리의 .github 폴더에 copilot-instructions.md라는 파일을 두면, 이 리포지토리에서 하는 채팅에 자동으로 붙어요. 제대로 적용됐는지는 Copilot 답변의 References를 펼쳐서 이 파일이 들어 있는지 보면 돼요. 루트에 AGENTS.md를 두는 방법도 있어요. 3-2에서 직접 만들고, 7교시에는 팀 규칙으로 키워요.

### 반복하는 일은 파일로 재사용합니다

| 종류 | 위치 | 쓰는 법 | 오늘 |
|---|---|---|---|
| 지침 파일 | .github/copilot-instructions.md | 항상 자동 적용 | 3-2, 7-3 |
| 프롬프트 파일 | .github/prompts/이름.prompt.md | /이름 으로 실행 (Local 하네스) | 3-3 /idea |
| 스킬 | .github/skills/이름/SKILL.md | /이름 또는 요청이 맞으면 자동 | 소개 |
| 사용자 지정 에이전트 | .github/agents/이름.agent.md | Agent 선택기에서 고름 | 소개 |

Copilot에게 반복해서 시키는 일은 파일로 만들어 팀과 함께 쓸 수 있어요. 지침 파일은 항상 자동으로 붙는 규칙이에요. 프롬프트 파일은 자주 쓰는 요청을 파일로 저장해 두고 슬래시 이름으로 실행하는 거예요. 주의할 점은, VS Code 문서에 따르면 프롬프트 파일은 Local 하네스에서만 실행돼요. 그래서 3-3에서는 새 채팅의 Session Target을 Local로 바꿔서 실행해요. 다른 하네스에서도 재사용하려면 스킬을 써요. 사용자 지정 에이전트는 역할과 쓸 도구를 정해 둔 나만의 에이전트예요. 이 둘은 오늘은 소개만 해요.

### 프롬프트 파일로 업무 아이디어를 검토합니다

전체 내용은 [실습 3-3](lab-3.md)에 있습니다.

```text
아이디어 3개: 줄어드는 일, 난이도, 위험
먼저 만들 것: 이유, 입력, 처리, 출력, 확인 방법
확인 필요: 글에 없어서 정하지 못한 것
규칙: 없는 숫자나 효과를 지어내지 않는다.
```

설문에서 아이디어 검토와 업무 자동화를 원하신 분이 많았어요. 그래서 프롬프트 파일을 아이디어 검토 도구로 만들어요. 업무 설명을 선택하고 /idea를 실행하면, 아이디어 세 개를 줄어드는 일과 난이도와 위험으로 비교하고, 무엇부터 만들지와 결과를 어떻게 확인할지를 답해요. 핵심은 마지막 규칙이에요. 글에 없는 절감 시간이나 효과를 지어내지 말라고 해요. 정해지지 않은 건 확인 필요로 나와요. 총무팀의 월간 집계 업무로 연습하고, 내 업무로도 한 번 해 봐요. 이때 회사 이름, 고객 정보, 실제 수치는 쓰지 않아요.
