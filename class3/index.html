    3교시. 프롬프트와 맥락 설계¶

    이번 교시의 목표

    좋은 프롬프트 구조로 요구사항을 정리하고, 지침 파일로 Copilot의 답을 일관되게 만들고, 스킬로 업무 아이디어를 검토할 수 있습니다.

    구간 시간
    이론 15분
    실습 3-1 ~ 3-3 35분

    실습 페이지:

    • 실습 3-1 회의록에서 사용자 스토리 뽑기
    • 실습 3-2 지침 파일 만들기
    • 실습 3-3 스킬로 아이디어 검토

    교안¶

    사용자 스토리: 누가, 무엇을, 왜 원하는지 한 문장으로¶

    스토리는 회사마다 부르는 이름이 다릅니다

    애자일, 스크럼으로 일하는 개발팀은 사용자 스토리, 줄여서 스토리라고 부릅니다. Jira 같은 도구에도 이슈 종류로 "Story"가 있습니다. 전통적인 방식이나 비개발 부서에서는 요구사항, 기능, 과제, 티켓, 건이라고 더 많이 부릅니다. 오늘 말하는 "스토리"는 요구사항 한 건이라고 생각하면 됩니다.

    회의록의 결정 사용자 스토리로 바꾸면
    겹치는 예약을 막는다 회의실을 예약하는 직원으로서, 이미 예약된 시간에는 예약이 안 되기를 원한다. 회의실 앞에서 누가 먼저 예약했는지 다투지 않기 위해서이다.

    인수 조건 (다 됐는지 판단하는 기준)

    • 10:00~11:00 예약이 있으면 10:30~11:30은 "이미 예약된 시간"으로 실패
    • 11:00~12:00은 성공 (끝과 시작이 맞닿는 것은 겹침이 아님)
    언제 무엇
    3-1 회의록의 결정 4개를 스토리 4개로 씁니다
    5-1 PM이 스토리를 이슈 S1~S4로 등록합니다
    5-2 각자 이슈 하나를 맡아 story-번호 브랜치에서 구현합니다
    6-1 PR에 Closes #번호, BA가 인수 조건으로 검토해 병합하면 이슈가 닫힙니다

    3교시 실습에서 회의록으로 사용자 스토리를 만들어요. 먼저 스토리가 뭔지 짚을게요. 스토리는 쉽게 말해 요구사항 한 건이에요. 애자일로 일하는 개발팀은 사용자 스토리, 줄여서 스토리라고 부르고, Jira 같은 도구에도 Story라는 이슈 종류가 있어요. 전통적인 방식이나 비개발 부서에서는 요구사항, 기능, 과제, 티켓, 건이라고 더 많이 불러요. 같은 걸 가리키는 말이에요.

    사용자 스토리는 기능 요구를 사용자 입장에서 한 문장으로 쓴 거예요. 누구로서, 무엇을 원한다, 왜냐하면, 이 세 가지를 담아요.

    회의록에는 '겹치는 예약을 막는다'라고만 적혀 있어요. 이걸 스토리로 바꾸면 화면처럼 돼요. 그리고 인수 조건은 그 스토리가 다 됐는지 판단하는 기준이에요. 확인할 수 있는 예로 써요.

    '겹침 검사 구현'이라고만 쓰면 누구를 위한 일인지, 어디까지 하면 끝인지가 빠져요. 스토리와 인수 조건으로 쓰면 만드는 사람과 검토하는 사람이 같은 기준으로 확인해요. 스토리 하나가 GitHub 이슈 하나가 돼요. 오후에 이걸 이슈로 만들어 나눠 구현해요.

    좋은 프롬프트는 목표, 맥락, 형식, 제약을 담습니다¶

    이렇게 쓰면 Copilot이 범위와 형식을 마음대로 정합니다.

    회의록 보고 사용자 스토리 만들어 줘

    이렇게 쓰면 더 좋습니다.

    [목표] 회의록의 '결정한 것' 4개를 사용자 스토리로 만들어 줘.
[맥락] docs/01_킥오프_회의록.md, 사용자는 회의실을 예약하는 직원과 총무팀이야.
[형식] 스토리마다 '누구로서, 무엇을, 왜' 한 줄 + 인수 조건 2개, 표로.
[제약] 회의록에 없는 정책은 정하지 말고 '확인 필요'로 표시해.

    같은 일을 시켜도 프롬프트에 따라 결과가 크게 달라져요. '회의록 보고 스토리 만들어 줘'라고만 하면 Copilot이 범위도 형식도 마음대로 정해요. 네 가지를 담아 보세요. 무엇을 원하는지 목표, 어떤 자료를 보고 누구를 위한 것인지 맥락, 어떤 모양으로 받고 싶은지 형식, 하지 말아야 할 것 같은 제약이에요. 특히 제약의 '회의록에 없는 정책은 정하지 말고 확인 필요로 표시해'가 오늘 아주 중요해요.

    GitHub 문서가 권하는 프롬프트 전략¶

    전략 뜻 오늘 예
    Start general, then get specific 넓게 시작해 구체적으로 목표 한 줄 → 조건 추가
    Give examples 예시를 준다 스토리 예시 1개 (few-shot)
    Break complex tasks 큰 일은 쪼갠다 계획 → 구현 → 테스트
    Avoid ambiguity 모호함을 피한다 '그거' 대신 파일, 함수 이름
    Provide relevant context 관련 맥락을 준다 회의록 첨부, #codebase
    Keep history relevant 대화 기록을 관련 있게 주제가 바뀌면 새 채팅
    Review Copilot's output 결과를 검토한다 실행, 근거, 테스트

    GitHub 문서 'Prompt engineering for GitHub Copilot Chat'에 나오는 전략들이에요. 문서에는 아홉 개가 있는데 오늘 쓰는 일곱 개만 골랐어요. 넓게 시작해서 구체적으로 좁히고, 예시를 주고, 큰 일은 쪼개고, '그거' 같은 모호한 말 대신 파일 이름을 쓰고, 관련 맥락을 붙이고, 주제가 바뀌면 새 채팅을 열고, 결과는 꼭 검토해요. 나머지 둘은 '실험하고 반복하기'와 '좋은 코드 습관 따르기'예요.

    예시를 주면 원하는 모양으로 답합니다: zero-shot과 few-shot¶

    예시 없이 요청하는 걸 zero-shot, 예시를 몇 개 함께 주는 걸 few-shot이라고 해요. GH-300 시험 범위에도 있는 용어예요. 예시가 없으면 Copilot이 형식을 마음대로 정해서 매번 모양이 달라져요. '이런 모양으로 써 줘' 하고 스토리 예시 하나만 붙여도 형식, 말투, 길이가 맞춰져요. 3-1에서 두 가지를 직접 비교해 봐요.

    맥락에 없는 결정을 Copilot이 채워 넣을 수 있습니다¶

    회의록에는 결정하지 못한 것이 세 개 있어요. 최대 예약 시간, 노쇼 자동 취소 기준, 현황판 연락처 공개예요. 그런데 Copilot에게 스토리를 만들어 달라고 하면, 이걸 '최대 2시간까지'처럼 그럴듯하게 정해 버리는 경우가 많아요. 이렇게 사실이 아닌 걸 그럴듯하게 만드는 걸 환각이라고 해요. 기획 문서에서 이게 제일 위험해요. 아무도 결정하지 않은 정책이 요구사항이 돼 버리니까요. 대책은 프롬프트 제약에 '정하지 말고 확인 필요로 표시해'를 넣고, 결과를 회의록과 대조하는 거예요.

    지침 파일: 매번 하는 말을 파일 하나로¶

    .github/copilot-instructions.md
    # 회의실 예약 서비스 지침

- 답변은 한국어로 한다.
- 오류 메시지는 한국어 문장으로 쓴다.
- 기능을 바꾸면 tests/에 pytest 테스트를 추가한다.
- 회의록에 없는 정책은 정하지 말고 질문한다.
- data/reservations.json은 요청할 때만 바꾼다.
    왜 .github 폴더에, 왜 .md 파일로 쓰나요?

    .github 폴더

    • .github는 GitHub와 도구가 읽는 설정을 모아 두는 폴더입니다. 오늘 쓰는 자동 테스트 .github/workflows/ci.yml도 여기에 있습니다.
    • Copilot은 정해진 자리에서 지침을 찾습니다. 리포지토리의 .github/copilot-instructions.md가 그 자리입니다. 이름이나 위치가 다르면 읽지 않습니다.
    • 리포지토리 안에 있으니 커밋하면 팀원 모두가 같은 지침을 받습니다. 바뀐 이력도 커밋으로 남습니다.
    • 이름 앞의 점(.)은 "설정용 폴더"라는 표시입니다. Mac의 Finder에서는 기본으로 숨겨져 보이지 않지만, VS Code 탐색기에는 보입니다.

    .github 폴더에 두는 대표 파일 (GitHub 공식 문서 기준)

    파일 하는 일 위치 규칙
    .github/workflows/*.yml GitHub Actions 워크플로 (오늘 ci.yml, pages.yml) 이 폴더에만 둡니다
    .github/copilot-instructions.md Copilot 리포지토리 지침 (3-2) 이 위치에만 둡니다
    .github/instructions/*.instructions.md 특정 파일에만 적용하는 Copilot 지침 이 폴더 아래
    .github/dependabot.yml 의존성 자동 업데이트 설정 이 폴더에만 둡니다
    .github/ISSUE_TEMPLATE/ 이슈를 만들 때 나오는 양식 이 폴더
    pull_request_template.md PR을 만들 때 나오는 양식 .github, 루트, docs 중 하나
    CODEOWNERS 파일별 리뷰 담당자 .github, 루트, docs 중 하나. 여러 곳에 있으면 .github가 먼저
    CONTRIBUTING.md, SECURITY.md 등 기여 방법, 보안 신고 안내 .github, 루트, docs 중 하나. .github가 먼저

    정리하면, 어떤 파일은 .github에만 두어야 하고, 어떤 파일은 여러 곳 중 하나를 고를 수 있지만 겹치면 .github가 먼저 쓰입니다. 그래서 GitHub와 도구를 위한 설정은 .github에 모아 두는 것이 일반적입니다. 문서에서는 이 폴더를 "숨김 폴더(hidden directory)"라고도 부릅니다.

    .md(Markdown) 파일

    • Markdown은 # 제목, - 목록 같은 간단한 기호로 구조를 표시하는 글 형식입니다. 메모장으로 열어도 그대로 읽힙니다.
    • 사람도 읽기 쉽고, Copilot 같은 언어 모델도 제목과 목록으로 나뉜 글을 잘 따릅니다.
    • GitHub 웹 화면에서 열면 제목과 목록이 보기 좋게 표시됩니다. 오늘 쓰는 docs/ 문서와 README도 모두 Markdown입니다.
    • 프로그램 문법이 아니라 글이라서, 개발을 몰라도 규칙을 쓰고 고칠 수 있습니다.

    매번 '한국어로 답해 줘, 테스트도 추가해 줘'라고 반복하지 않으려면 지침 파일을 만들어요. 리포지토리의 .github 폴더에 copilot-instructions.md라는 파일을 두면, 이 리포지토리에서 하는 채팅에 자동으로 붙어요. 제대로 적용됐는지는 Copilot 답변의 References를 펼쳐서 이 파일이 들어 있는지 보면 돼요. 루트에 AGENTS.md를 두는 방법도 있어요.

    왜 .github 폴더일까요? 워크플로, 이슈 양식, PR 양식처럼 GitHub와 도구가 읽는 파일을 모아 두는 정해진 자리예요. 리포지토리에 커밋되니까 팀원 모두가 같은 지침을 받아요. 왜 .md일까요? 지침은 코드가 아니라 사람 말로 쓰는 글이에요. 마크다운은 사람도 모델도 읽기 쉽고 GitHub에서 보기 좋게 보여요.

    3-2에서는 이 내용을 복사하지 않아요. 내가 꼭 넣을 규칙을 Copilot에게 말하고, Ask로 제안과 질문을 받고, 사람이 고른 규칙만 Agent가 파일로 저장해요. 그다음 사람이 검토해요. 7교시에는 팀 규칙으로 키워요.

    반복하는 일은 파일로 재사용합니다¶

    종류 위치 쓰는 법 오늘
    지침 파일 .github/copilot-instructions.md 항상 자동 적용 3-2, 7-3
    경로별 지침 .github/instructions/이름.instructions.md applyTo 경로의 파일에 자동 소개
    스킬 .github/skills/이름/SKILL.md /이름 또는 요청이 맞으면 자동 3-3 /idea
    사용자 지정 에이전트 .github/agents/이름.agent.md Agent 선택기에서 고름 소개

    Copilot에게 반복해서 시키는 일은 파일로 만들어 팀과 함께 쓸 수 있어요. 리포지토리에 많이 두는 순서대로 보면, 먼저 지침 파일이에요. 항상 자동으로 붙는 규칙이에요. 경로별 지침은 applyTo로 정한 파일, 예를 들어 파이썬 파일을 다룰 때만 붙는 규칙이에요. 스킬은 반복하는 작업 하나의 순서와 형식을 담아요. 슬래시 이름으로 부르거나, 요청이 설명과 맞으면 Copilot이 스스로 불러와요. 사용자 지정 에이전트는 역할과 쓸 도구를 정해 둔 나만의 에이전트예요. 오늘은 지침 파일과 스킬을 직접 만들어요.

    스킬은 한 번 만들면 여러 곳에서 씁니다¶

    어디서 리포지토리 내 컴퓨터
    GitHub Copilot (VS Code, CLI, 클라우드 에이전트, 코드 리뷰) .github/skills/ ~/.copilot/skills/
    Claude .claude/skills/ ~/.claude/skills/
    OpenAI Codex .agents/skills/ ~/.agents/skills/

    스킬은 GitHub만의 기능이 아니에요. Agent Skills라는 개방형 표준이라서, SKILL.md가 든 폴더라는 같은 형식을 여러 AI 도구가 읽어요. 그래서 한 번 익혀 두면 다른 도구에서도 그대로 써요. 오늘은 GitHub Copilot 기준으로 .github/skills에 만들어요. 리포지토리에 커밋하면 VS Code뿐 아니라 github.com의 클라우드 에이전트와 코드 리뷰도 같은 스킬을 쓸 수 있어요. GitHub Copilot은 .claude/skills나 .agents/skills에 있는 스킬도 읽어요. 다만 남이 만든 스킬을 받아 올 때는 GitHub가 검증하지 않으니, 숨은 지시가 없는지 내용을 먼저 열어 봐요. 자세한 표와 주의점은 실습 3-3에 있어요.

    스킬로 업무 아이디어를 검토합니다¶

    전체 내용은 실습 3-3에 있습니다.

    /idea #04_월간집계_업무.md

아이디어 3개: 줄어드는 일, 난이도, 위험
먼저 만들 것: 이유, 입력, 처리, 출력, 확인 방법
확인 필요: 글에 없어서 정하지 못한 것
규칙: 없는 숫자나 효과를 지어내지 않는다.

    설문에서 아이디어 검토와 업무 자동화를 원하신 분이 많았어요. 그래서 스킬로 아이디어 검토 도구를 만들어요. 머리말에 name과 description을 써요. name은 명령 이름이고 폴더 이름과 같아야 해요. description은 무엇을 하고 언제 쓰는지예요. 업무 설명 파일을 붙여 /idea를 실행하면, 아이디어 세 개를 줄어드는 일과 난이도와 위험으로 비교하고, 무엇부터 만들지와 결과를 어떻게 확인할지를 답해요. 핵심은 마지막 규칙이에요. 글에 없는 절감 시간이나 효과를 지어내지 말라고 해요. 정해지지 않은 건 확인 필요로 나와요. 총무팀의 월간 집계 업무로 연습하고, 내 업무로도 한 번 해 봐요. 이때 회사 이름, 고객 정보, 실제 수치는 쓰지 않아요. /idea 없이 '이 업무 자동화 아이디어 검토해 줘'라고만 해도, 요청이 description과 맞으면 Copilot이 스킬을 불러와요. 이것도 확인해 봐요.
