    5교시. 팀 실습 ① 요구에서 구현까지¶

    교육 목표

    역할에 따라 Copilot으로 요구를 정리하고 나눠 각자 기능을 구현할 수 있다.

    이론 10분 실습 40분 (미션 5-1 15분, 미션 5-2 22분, 미션 5-3 3분) 실습 장소 팀 리포지토리 room-booking-team<번호>

    시간표¶

    시간 무엇을 페이지
    10분 5교시 흐름, 역할 카드, 팀 백로그 설명 이 페이지
    15분 미션 5-1 요구 정리와 분배 미션 5-1
    22분 미션 5-2 스토리 구현 미션 5-2
    3분 미션 5-3 클라우드 에이전트에 맡기기 미션 5-3

    교안¶

    이번 교시를 시작하며

    • 왜 지금 하나요? 오전에는 혼자서 브랜치, /plan, Agent 구현, 검토, 테스트, PR까지 해 봤습니다. 실제 일은 여럿이 같은 리포지토리에서 합니다. 누가 무엇을 결정하고, 일을 어떻게 나누고, 어디서 부딪히는지를 팀으로 겪어 봅니다.
    • 앞에서 만든 무엇을 쓰나요? 4-4에서 PO가 만든 팀 리포지토리와 그 안의 docs/ 폴더(현업 요청, 킥오프 회의록, 현행 업무), 3교시에 배운 사용자 스토리와 인수 조건, 4교시의 구현 흐름을 그대로 씁니다.
    • 끝나면 무엇을 넘기나요? 이슈 S1~S4(인수 조건 포함)와, 각자 자기 브랜치 story-<번호>에 커밋된 구현을 6교시에 넘깁니다. 6교시에 PR을 열고 리뷰하고 병합합니다.

    사용자 스토리가 이슈가 되고, PR로 닫힙니다¶

    3교시에 쓴 사용자 스토리가 오후에는 일의 단위가 됩니다. 스토리 하나가 GitHub 이슈 하나이고, 이슈 하나를 한 사람이 맡아 PR 하나로 끝냅니다.

    flowchart TB
    A["사용자 스토리<br/>누구로서, 무엇을, 왜 + 인수 조건"] --> B["이슈 #3 (S1)<br/>PM이 등록, 담당자 1명"]
    B --> C["브랜치 story-3<br/>담당자가 Agent로 구현, 테스트"]
    C --> D["PR 본문에 Closes #3<br/>BA가 인수 조건으로 검토"]
    D --> E["병합하면 이슈 #3 자동으로 닫힘"]

    이슈 본문은 이런 모양입니다.

    제목: S1 겹치는 예약 막기

## 스토리
회의실을 예약하는 직원으로서, 이미 예약된 시간에는 예약이 안 되기를 원한다.
회의실 앞에서 누가 먼저 예약했는지 다투지 않기 위해서이다.

## 바꿀 곳
booking/rules.py

## 인수 조건
- 10:00~11:00 예약이 있으면 10:30~11:30은 "이미 예약된 시간"으로 실패
- 11:00~12:00은 성공 (끝과 시작이 맞닿는 것은 겹침이 아님)

    인수 조건은 BA가 Copilot으로 초안을 만들고 사람이 확정합니다. 이 인수 조건이 6교시 PR 검토의 기준이 됩니다. 이슈가 모두 스토리는 아닙니다. 6-3의 변경 요청(CR-001)이나 5-3에서 클라우드 에이전트에게 맡기는 작업도 이슈로 만듭니다.

    클라우드 에이전트: 이슈를 맡기면 PR로 돌아옵니다¶

    github.com에서 이슈의 Assignees에 Copilot을 지정하면, 클라우드 환경에서 작업하고 끝나면 PR을 엽니다. 내 컴퓨터를 꺼도 일합니다. AI Credits와 Actions 사용 시간을 함께 쓰니 팀당 한 건만 맡깁니다. 5교시 끝에 테스트와 사용 설명 추가를 맡기고, 7교시에 결과를 검토합니다.

    flowchart TB
    A["이슈 작성"] --> B["Assignees: Copilot"]
    B --> C["클라우드에서 작업"]
    C --> D["변경 내용 읽기"]
    D --> E["Approve and run workflows"]
    E --> F["Ready for review"]
    F --> G["맡긴 사람이 아닌 팀원이 승인, 병합"]

    5교시 흐름¶

    flowchart TB
    A["PO<br/>Copilot으로 MVP 우선순위와<br/>결정안 초안"] --> B["강사(현업)에게<br/>결정 못 한 정책 질문"]
    B --> C["PM<br/>라벨 스토리, 이슈 S1~S4,<br/>담당자 1명씩"]
    C --> D["BA<br/>Copilot으로 인수 조건 초안,<br/>사람이 검토해 이슈에"]
    C --> E["개발자<br/>Copilot으로 바꿀 파일과<br/>충돌 위험 분석"]
    D --> F["모두<br/>story-번호 브랜치에서<br/>Agent로 구현과 테스트"]
    E --> F
    F --> G["6교시로<br/>PR, 리뷰, 병합"]

    모두 Copilot으로 구현합니다¶

    이 과정의 역할극은 GitHub 기초 과정과 다릅니다. 역할이 무엇이든 모두 스토리 하나씩을 Copilot으로 구현합니다. 역할은 그 위에 얹는 책임입니다.

    질문 누가
    무엇부터 할지, 정책을 어떻게 할지 결정하나요? PO
    이슈, 담당자, 병합 순서를 정리하나요? PM
    다 됐는지를 인수 조건으로 검토하나요? BA
    바꿀 파일과 충돌, 기술 위험을 분석하나요? 개발자

    Copilot은 초안, 사람은 결정

    오늘 오후에 Copilot은 결정안 초안, 인수 조건 초안, 영향 분석, 코드, 테스트, 리뷰 댓글을 만듭니다. 그것을 받아들일지 정하는 것은 사람입니다. 특히 회의록에 없는 정책은 Copilot이 정하지 않습니다. 현업(오늘은 강사)에게 묻습니다.

    팀 백로그¶

    현업 요청과 킥오프 회의록의 "결정한 것"에서 나온 스토리 4개입니다. 3인 팀은 S4를 뺍니다.

    번호 스토리 바꿀 곳 완료 기준(인수 조건 예)
    S1 같은 회의실, 같은 날짜에 시간이 겹치는 예약을 막는다 booking/rules.py 10:00~11:00이 있으면 10:30~11:30은 "이미 예약된 시간"으로 실패. 11:00~12:00은 성공(맞닿음은 겹침 아님)
    S2 회의실 정원을 넘는 예약을 막는다 booking/rules.py 소회의실 A(정원 4)에 5명이면 "정원을 넘었습니다"로 실패
    S3 예약을 취소할 수 있다 booking/service.py, booking/__main__.py python -m booking cancel --id 3이면 #3이 목록에서 사라지고 "[취소 완료]" 출력. 없는 번호면 "[취소 실패] 없는 예약 번호입니다"
    S4 18:00에 끝나는 예약이 되게 고친다 booking/rules.py 17:00~18:00 성공, 17:30~18:30 실패

    S1, S2, S4는 같은 파일을 고칩니다

    세 사람이 동시에 booking/rules.py와 tests/test_rules.py를 고치면 6교시 병합 때 충돌이 날 수 있습니다. 실제 일에서도 자주 생기는 일이라 일부러 그대로 둡니다. 5-1에서 개발자가 이 위험을 미리 찾고, 6-1에서 충돌을 Copilot과 함께 해결합니다.

    S1과 S4는 오전에 개인 리포지토리에서 해 본 것입니다. 해 본 사람이 맡으면 빠르고, 처음 하는 S2, S3도 같은 흐름이라 막히지 않습니다.

    역할 카드¶

    미션을 시작하기 전에 내 역할 카드를 읽습니다. 3인 팀은 PO가 PM 카드도 함께 맡습니다. 모든 역할은 카드의 일과 별도로 스토리 하나를 구현합니다.

    한 줄 정의: 제품 책임자. 무엇을, 왜 만들지 정하고 정책을 최종 결정합니다.

    하는 일

    • 결정 4개 중 MVP 우선순위를 정합니다. (5-1)
    • 결정 못 한 정책 3개의 결정안을 만들고, 현업(강사)에게 확인해 이슈 댓글로 남깁니다. (5-1)
    • 6-3 변경 요청 CR-001을 이슈로 등록합니다.

    Copilot에게 시킬 일 (예시)

    #codebase docs/01_킥오프_회의록.md의 "결정한 것" 4개를 MVP 우선순위로 정리하고, "결정하지 못한 것" 3개에 대해 PO 결정안 초안과 현업에게 물어볼 질문을 만들어 주세요.

    받는 것과 넘기는 것

    받는 것 누구에게서 넘기는 것 누구에게
    현업 요청, 회의록 docs/ 폴더 우선순위, 정책 결정 댓글 팀 전체
    정책 답변 강사(현업) 결정 기록 PM, BA

    한 줄 정의: 진행 관리자. 언제, 누가 할지 정리하고 병합을 관리합니다.

    하는 일

    • 라벨 스토리를 만들고 이슈 S1~S4를 등록합니다. (5-1)
    • 이슈마다 담당자(Assignees)를 1명씩 정합니다. 전원이 하나씩입니다. (5-1)
    • 6교시에 CI가 초록이고 BA가 승인한 PR을 순서대로 병합합니다. (6-1)
    • 5교시 끝에 클라우드 에이전트에게 맡길 이슈를 씁니다. (5-3)

    Copilot에게 시킬 일 (예시)

    팀 백로그 S1~S4를 GitHub 이슈로 등록하려고 합니다. 각 이슈의 제목과 본문(스토리 한 줄, 바꿀 파일, 완료 기준)을 만들어 주세요. 근거는 docs/00_현업요청.md입니다.

    받는 것과 넘기는 것

    받는 것 누구에게서 넘기는 것 누구에게
    우선순위 PO 이슈 S1~S4, 담당자 팀 전체
    승인된 PR BA 병합 결과 팀 전체

    한 줄 정의: 업무 분석가. 구체적으로 무엇이 되어야 다 된 것인지 정하고 검토합니다.

    하는 일

    • 이슈 S1~S4의 인수 조건(Given-When-Then) 초안을 Copilot으로 만들고, 직접 검토해 이슈 본문에 붙입니다. (5-1)
    • 6교시에 PR을 인수 조건으로 검토하고 Approve합니다. (6-1)
    • 6-3에서 CR-001 영향 분석을 합니다.

    Copilot에게 시킬 일 (예시)

    아래 스토리의 인수 조건을 Given-When-Then 형식으로 3개 써 주세요. 경계값(맞닿은 시간, 정원과 같은 인원)을 하나 이상 넣어 주세요. 문서에 없는 정책은 만들지 말고 "확인 필요"로 표시해 주세요.

    받는 것과 넘기는 것

    받는 것 누구에게서 넘기는 것 누구에게
    이슈 S1~S4 PM 인수 조건 담당자 전원
    PR 담당자 리뷰, Approve PM

    한 줄 정의: 기술 담당. 바꿀 파일과 기술 위험을 미리 보고 팀을 돕습니다.

    하는 일

    • 스토리마다 바꿀 파일과 충돌 위험을 Copilot으로 분석해 이슈 댓글로 남깁니다. (5-1)
    • 팀원이 구현하다 막히면 함께 봅니다. (5-2)
    • 6-2에서 배포 워크플로를 Copilot으로 만들고, 6-3에서 CR-001을 구현합니다.

    Copilot에게 시킬 일 (예시)

    #codebase 스토리 S1~S4를 구현하면 각각 어떤 파일의 어떤 함수가 바뀌는지 표로 정리하고, 같은 파일을 동시에 고쳐 병합 충돌이 날 위험이 있는 조합을 알려 주세요.

    받는 것과 넘기는 것

    받는 것 누구에게서 넘기는 것 누구에게
    이슈 S1~S4 PM 바꿀 파일, 충돌 위험 댓글 팀 전체, PM
    병합된 main PM 배포 워크플로 팀 전체

    크레딧 아껴 쓰기¶

    • 모델은 Auto로 둡니다. 자동 모델 선택은 모델 비용이 10% 할인됩니다.
    • Chat과 Agent는 AI Credits를 씁니다. 같은 질문을 여러 번 다시 보내지 말고, 답을 고쳐 달라고 이어서 요청합니다.
    • 6교시 Copilot 코드 리뷰(1회 약 150크레딧, Balanced 기준)는 각자 자기 PR에 1회만 합니다.
    • 7교시 클라우드 에이전트는 팀당 1건만 맡깁니다.

    이번 교시 정리¶

    • 역할은 결정(PO), 정리(PM), 검토(BA), 분석(개발자)이고, 구현은 모두가 Copilot으로 합니다.
    • Copilot의 초안은 사람이 검토해 이슈에 남깁니다. 문서에 없는 정책은 현업에게 묻습니다.
    • S1, S2, S4는 같은 파일을 고쳐 충돌이 날 수 있습니다. 6교시에 해결합니다.
